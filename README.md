# WireGuard tools for ZimaOS

**Version 1.1.3** · ZimaOS 1.8.0 (amd64) · sysext module `wireguard`

The ZimaOS kernel has WireGuard (`CONFIG_WIREGUARD=m`), but not the tools to use it. This module adds them:

- `wg` and `wg-quick` from [wireguard-tools](https://git.zx2c4.com/wireguard-tools) **v1.0.20260223**, built from source (Debian 13 ships 1.0.20210914);
- `wireguard@.service` — `wg-quick@.service` from wireguard-tools, reading `/DATA/AppData/wireguard/<name>.conf`;
- `wireguard-zima` — turns a config into a tunnel that also comes back after a reboot;
- the **WireGuard** tile on the dashboard (`wireguard-web`).

## The tile

Create a tunnel (a key pair is generated on the host), turn it on and off (on = also at every boot), see each peer's last handshake and traffic from `wg show`, and **add a client**: the tile picks the next free address, generates the client's keys and shows its config once — to import in the WireGuard app or download; the client's private key is not kept on the host. A peer with its own key (another server) can be added too. Deleting a tunnel moves its config to `/DATA/AppData/wireguard/.deleted/`. **With ZFW installed, turning a tunnel on opens its listen port there** (an allow rule with the id `mod-udp-<port>`, saved, applied and committed, so it survives a reboot); turning it off or deleting it removes exactly that rule again. Tunnel names start with `wg`: ZFW lets traffic inside a tunnel through only on `wg*` interfaces. A tunnel turned on with `wireguard-zima` on the command line does not touch ZFW.

**Clients reach the internet and the LAN** (since 1.1.3): a tunnel the tile creates gets three lines in `[Interface]` that set NAT for its clients, as wg-easy and PiVPN do:

```ini
# NAT for clients (WireGuard tile): they reach the internet and the LAN through this host
PostUp = /bin/sh /usr/libexec/wireguard/nat.sh up %i
PostDown = /bin/sh /usr/libexec/wireguard/nat.sh down %i
```

`nat.sh` turns on IPv4 forwarding and sets a MASQUERADE rule for the tunnel's subnet plus two FORWARD rules per uplink (the interface of the default route): from the tunnel to the uplink, and the answers back. Each is marked `wgzima-nat-<tunnel>`, in the iptables backend Docker uses. The FORWARD rules are appended, so Docker's chains and ZFW decide first: they open no way to a container's unpublished port and none past ZFW. ZFW itself lets traffic from interfaces named `wg*` through (its rule `-i wg+ -j RETURN` in DOCKER-USER), so clients of a tunnel with such a name reach what the LAN reaches, with or without NAT. Without NAT a client connects, but its packets leave the host with its tunnel address and the router has no way back: no internet, no LAN (tunnels created with 1.1.2 or older). The tile shows **Clients reach the internet and the LAN: on/off** for each tunnel; *Turn on* adds the lines to an older tunnel and, if it is running, sets the rules at once without dropping it. A client added with "send all of the client's traffic through the tunnel" while NAT is off gets a warning. In a config of your own, add the three lines by hand; `sh /usr/libexec/wireguard/nat.sh status <tunnel>` prints how many rules are set (3 when on, with one uplink).

Measured on ZimaOS 1.8.0 (ZimaBoard 2) with ZFW active, 2026-10-23: turned on in Chrome, the tile opened UDP 51885 in ZFW; a client config generated by the tile, started with `wg-quick` in a network namespace, reached the host through the tunnel with no other firewall rule (TCP answer, handshake on the host side); turning off removed the rule again.

## Use

```sh
sudo mkdir -p /DATA/AppData/wireguard
sudo nano /DATA/AppData/wireguard/wg0.conf     # a normal wg-quick config; the file name is the interface name
sudo wireguard-zima enable wg0                 # start now and at every boot
wireguard-zima status wg0
sudo wireguard-zima disable wg0                # stop, no longer at boot
```

`wg genkey | tee privatekey | wg pubkey > publickey` makes a key pair. `systemctl reload wireguard@wg0` applies a changed peer list without dropping the tunnel (`wg syncconf`).

### Why `enable` and not `systemctl enable`

A unit inside a sysext is not started at boot on ZimaOS: `multi-user.target` is resolved before the extension is merged into `/usr`. `wireguard-zima enable` therefore writes a small timer to `/etc/systemd/system` (persistent) that starts `wireguard@<name>` 15 seconds after boot if it is not running — lintux-modkit's `sysext/unit-watchdog.sh`. Run `sudo wireguard-zima disable <name>` before removing the module, so no timer is left behind.

### Firewall (ZFW)

ZFW drops incoming traffic it does not know. Its rules accept traffic **inside** interfaces named `wg*`, but not the UDP port the tunnel listens on (`ListenPort`). The tile opens that port when a tunnel is turned on; on the command line open it in ZFW yourself. A host that only dials out (a client config without `ListenPort`) needs nothing.

### Limits

- `DNS =` in a config needs `resolvconf`, which ZimaOS does not have — leave it out.
- No `nft` on ZimaOS: for full-tunnel routes (`AllowedIPs = 0.0.0.0/0`) `wg-quick` uses `iptables-restore`, which is there.

**Folder check** (since 1.1.1): `/DATA/AppData` is writable by everyone on ZimaOS 1.8 (mode 0777 without the sticky bit; the share of `/DATA` is writable over SMB), so another user could replace `/DATA/AppData/wireguard` with a folder of their own — and `wg-quick` runs a config's `PostUp` lines as root. Before a tunnel starts and before the tile reads a config, the module sets the sticky bit on `/DATA/AppData` (then only a folder's owner can rename it) and refuses a `wireguard` folder that is a symlink, not root's, or writable by others (lintux-modkit `appdata`). Since 1.1.3, a `/DATA` that another user owns (uid 999 on one ZimaOS 1.8 box — that user could rename `/DATA/AppData`) is given back to root, with the way back in the log.

## Install (on the ZimaOS host)

With the [Module Manager](https://github.com/chicohaager/modmanager) (v0.2.5 or later): tab **Catalog**, **WireGuard**, **Install** — it checks the release checksum and refuses an image that would replace files of ZimaOS. By hand:

```sh
cd /tmp
curl -fsSLO https://github.com/chicohaager/zimaos-wireguard-sysext/releases/latest/download/wireguard-amd64.raw
curl -fsSLO https://github.com/chicohaager/zimaos-wireguard-sysext/releases/latest/download/wireguard-amd64.raw.sha256
sha256sum -c wireguard-amd64.raw.sha256
mv wireguard-amd64.raw wireguard.raw        # zpkg takes the module name from the file name
sudo zpkg install /tmp/wireguard.raw
sudo systemctl daemon-reload
```

## Build and test

```sh
sh build.sh amd64              # docker, Go, node, squashfs-tools, ../lintux-modkit; wireguard-tools pinned by tag and commit
tools/check-reproducible.sh     # before a release: builds three times (umask 022, 002 and 077) and fails when the bytes differ
../lintux-modkit/tools/check-release.sh . v<version> wireguard# after the release: rebuilds the tag, same bytes as the asset
sudo sh tools/host-test.sh     # on the host after installing, with lintux-modkit tools/hosttest-lib.sh next to it;
                               # a failure or abort removes what it created, after a clean run `cleanup` does
```

`build.sh` builds only against the lintux-modkit commit in `lintux-modkit.ref`, without local changes — both for the scripts (`../lintux-modkit` or `LINTUX_MODKIT=`) and for the directory Go compiles (go.mod's `replace` or a `go.work`; `LINTUX_MODKIT` does not move it): `scripts/modkit-check.sh` asks `go list` which one that is. `MODKIT_DEV=1` builds anyway, with a warning, not for a release. `bash tools/test-modkit-check.sh` tests the check.

The host test builds a real tunnel: the peer runs in its own network namespace behind a veth pair; a TCP connection must fail before `enable` and get through after it, with a handshake. A second namespace stands in for the internet: it has no route back to the tunnel, so the peer reaches it only through NAT — the test checks that it answers with NAT, does not answer after `nat.sh down`, answers again after `nat.sh up`, and that a restart leaves the rules there once; every FORWARD rule names the uplink and comes after Docker's DOCKER-USER jump. Measured on ZimaOS 1.8.0 (ZimaBoard 2) with ZFW active, 2026-11-23: 15 OK, 0 FAIL; in Chrome, the tile created a tunnel with NAT on, turned NAT off and on again while it ran (3 rules on the host), and deleting it left 0 rules. The test opens the paths it needs in ZFW and removes exactly those again (`cleanup`).
